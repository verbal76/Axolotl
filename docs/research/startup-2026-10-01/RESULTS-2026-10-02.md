# Startup: results of the world-build work (2026-10-02/03)

Goal: the title is usable sooner on the phone, with the same world, the same game state and the same
picture. Everything is in OTA-delivered game code (scripts/world, scripts/core, tests); nothing
native changed (`python3 tools/ota_runtime.py --check`).

Two things were tried and dropped:
- **Deferring vegetation meshes (tufts, reeds, broadleaves, stem plants, corals, root strands).** These are instanced by MultiMeshes. A MultiMesh given a mesh whose surface comes later rendered differently: in the Vulkan Mobile title shot, 505 pixels were off by one level. These meshes are built immediately again (d3b4f02).
- **Deferring far balls, creatures, HUD or pause menu until after the title appears.** Rejected for this stream. Catalog ids, repopulation, food, the save restore, the Aquarium view and Treasure all need every ball. The world build uses the global random sequence, so the build order is fixed. A title that keeps building in the background would stutter, or would stall on Continue.

## Thread tasks added, and what each reads and writes

All run on Godot's WorkerThreadPool, the same pool the terrain heights have used since dev-000069. No new thread is created.

| Task | Reads | Writes |
|---|---|---|
| `MossBall.finalize_terrain` group task, one job per ground tile | The ball's hills, ravines and cells (`terrain_height`), `FACES`, `TILE_Q`, radius. Cells are built beforehand on the main thread. | Only its own `TileGeometry` slot: verts, norms, idx, faces, max_h. The main thread is blocked in `wait_for_group_task_completion` for the whole task. |
| The same group's last job: the far mesh | As above | One `PackedVector3Array`, appended to a local array the main thread reads after the wait |
| `MeshLib._commit` task, one per deferred mesh: stems (`stem_surface`), a ladder's leaves (`leaf_surface` + `_leaf_into`), platform leaves, `_triangles` for mounds, shelves, sweeps and caves | Only values captured into its lambda: numbers, Transform3Ds, and a ladder's list of leaf transforms (a local array the main thread no longer uses). `_triangles` reads its own duplicated vertex and UV arrays. | A SurfaceTool it creates and drops itself. Its result (`commit_to_arrays()`, flags, name, meta) goes into its own result array. The main thread touches that array only after `wait_for_task_completion`, at the end of the same ball. |

No task:
- calls the scene tree, PhysicsServer3D or RenderingServer;
- creates or frees a Node, ArrayMesh or Shape;
- reads or writes a static variable. `MeshLib._leaf_shapes`, `deferring` and `_deferred` are touched only on the main thread; worker code calls only pure static functions, with their own locals and constants.

Notes on shared objects:
- The only engine objects shared with the main thread are the result containers. Each has exactly one writer, and nobody reads it until that writer has finished.
- The lambdas use no `self`, so a task holds no reference to a LevelBuilder or MossBall. The exception is the terrain jobs, whose lambda reads the MossBall's terrain arrays while the main thread is blocked.

## Thread-safety rules relied on

- Worker threads never touch the scene tree, the physics server, the rendering server or any Resource that is already shared. Their only engine objects are their own SurfaceTool and packed arrays.
  - Workers produce plain data: terrain arrays, and `SurfaceTool.commit_to_arrays()` plus flags.
  - ArrayMesh surfaces, nodes, `ConcavePolygonShape3D.set_faces` and `add_child` all happen on the main thread.
- What workers read never changes while they run:
  - Terrain heights are read only inside `finalize_terrain`, after `_build_cells()`, while the main thread waits.
  - A deferred mesh is built only from its own arguments, copied into the job (packed arrays are duplicated).
  - Anything that reads terrain the layout may still change (mound, shelf and sweep ground callables, scatter accept callables) runs on the main thread when it is called, as before.
- Results are joined deterministically. Each job writes only its own slot. The main thread consumes the slots in the original order, so the outcome does not depend on thread timing. Three repeated startups gave the same hashes.
- `terrain_max_h` is a maximum, so the order in which tiles are combined does not change it.

## Timing

Desktop headless, `--startup-probe`, interleaved base and branch runs. The probe now also prints main-thread CPU, run-queue wait and whole-process CPU at each mark. This box has 4 vCPUs shared by four work streams, so the main-thread CPU column is the best guide to the phone's critical path. Wall time depends on how busy the box is.

| | base | branch |
|---|---|---|
| quieter box, 3+3 (ab7): balls wall | 8 272 ms | 6 002 ms |
| quieter box: balls main CPU | 6 577 ms | 2 600 ms |
| saturated box (load ≈ 9), 5+5 (final5): balls main CPU | 7 769 ms | 3 286 ms |
| saturated box: Game._ready → title usable main CPU | 8 474 ms | 4 138 ms |
| saturated box: Game._ready → title usable wall | 13 166 ms | 12 733 ms (main thread waited 4.6 s for a CPU) |
| all threads' CPU, balls | 9 440 ms | 7 930 ms |

Expected on the phone (dev-000069, balls 6.27 s, title usable ≈ 10.7 s):
- The main thread's work in balls 1-7 roughly halves, about −3 s.
- The work moved to worker threads runs on the phone's free cores.
- The phone should reach a usable title in roughly 7.5-8 s.

The phone's own Diagnostics timeline after this OTA is the confirmation still needed.

## Native-layer proposals (future APK, not done)

- `rendering/shader_compiler` and pipeline cache: check that the shader baker covers the Mobile variants of the world materials. On the phone, creatures, HUD and the first frame cost 0.5-1 s, against 0.1 s headless; that gap is render-side.
- Enable thread-safe physics (`physics/3d/run_on_separate_thread`) or a threaded rendering model. Collision shapes and mesh resources could then be made on worker threads too. Today they must stay on the main thread.
- `HEALTHY_AFTER_MS` and the engine start (0.6-0.7 s before the bootstrap) are native-only.
